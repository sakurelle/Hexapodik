Работай с текущей версией `RP2040RobotController`.

Текущую contact logic нужно переработать, а не продолжать латать.

На реальном роботе после команды он немного начинает движение и затем останавливается. Текущие host tests проходят, поэтому проблема в том, что тестовая модель контактов слишком идеальная для реальных NC механических микриков.

Не менять PIO/DMA, servo mapping, IK/FK и RC.

## 1. Главная проблема

Сейчас `GaitGenerator` слишком сильно зависит от мгновенных debounced contact levels:

* contact используется для liftoff;
* touchdown;
* ContactStuck;
* NoGround;
* canStartSwing();
* support polygon.

Из-за одного ненажатого или дребезжащего микрика может остановиться весь gait.

Переработать contact subsystem на event-based architecture.

## 2. ContactSensor должен выдавать события

Для каждой ноги хранить:

```cpp
struct ContactState {
    bool raw;
    bool stable;

    bool pressed_event;   // LOW -> HIGH
    bool released_event;  // HIGH -> LOW

    uint32_t stable_ms;

    bool healthy;
    uint32_t stuck_count;
};
```

События должны появляться только на один control tick после подтверждённого изменения состояния.

Напоминание по аппаратной логике:

```text
LOW  = стопа не касается пола
HIGH = стопа касается пола
```

NC + внешний pull-up 4.7k.

## 3. Сделать асимметричный debounce

Для механического микрика:

```cpp
constexpr uint32_t kContactPressDebounceMs = 10;
constexpr uint32_t kContactReleaseDebounceMs = 15;
```

То есть:

* HIGH должен быть стабильным 10 ms -> PRESSED;
* LOW должен быть стабильным 15 ms -> RELEASED.

Не использовать один `kContactDebounceMs` для обоих переходов.

Control loop 200 Hz, поэтому считать время через реальный `dt`, не через количество вызовов.

## 4. Убрать contact state machine из GaitGenerator

Не хранить:

```cpp
WaitingForRelease
Airborne
Touchdown
```

как интерпретацию самого GPIO.

Вместо этого gait должен иметь собственную механическую фазу ноги:

```cpp
enum class LegPhase {
    Stance,
    Lift,
    Transfer,
    Descend,
    GroundSearch
};
```

Это состояние траектории, а не состояние датчика.

ContactManager только сообщает события.

## 5. Новый lifecycle swing

### STANCE

Микрик здесь НЕ управляет gait phase напрямую.

Потеря контакта на несколько миллисекунд не должна останавливать робота.

### LIFT

Стопа начинает подниматься.

HIGH здесь нормально — нога ещё физически не успела оторваться.

`pressed_event` полностью игнорировать.

Когда появляется:

```text
released_event
```

записать:

```cpp
released_this_swing = true;
```

### TRANSFER

Нога переносится по XY.

Обычный touchdown здесь не принимать.

Если контакт возник после уже подтверждённого release слишком рано, считать это `EARLY_COLLISION`, но пока не делать global FAULT.

Для первой реализации просто остановить дальнейшее движение этой ноги вниз/в сторону и запросить controlled stop робота.

### DESCEND

Только здесь разрешён нормальный touchdown.

Условия touchdown:

```text
released_this_swing == true
AND
pressed_event == true
```

После touchdown:

```text
current target Z -> localGroundZ
закончить swing этой ноги
перевести её в STANCE
```

Никакого дополнительного движения вниз.

Early touchdown в начале DESCEND должен работать аналогично:
текущий Z становится новым ground level.

## 6. Late touchdown / GroundSearch

Если нога дошла до ожидаемого:

```text
expectedGroundZ
```

и контакта ещё нет:

не выдавать сразу FAULT_NO_GROUND.

Перейти:

```text
DESCEND -> GROUND_SEARCH
```

В `GROUND_SEARCH`:

* XY полностью зафиксирован;
* Z двигать вниз с постоянной небольшой скоростью:

```cpp
kGroundSearchSpeedMmS = 15.0f;
```

* предел:

```cpp
kGroundSearchMm = 15.0f;
```

Если появился `pressed_event`:

```text
-> STANCE
localGroundZ = currentZ
```

Если достигнут весь search range:

```text
NO_GROUND
```

Тогда остановить дальнейшее опускание ноги и запросить controlled gait stop.

## 7. SENSOR_STUCK_HIGH вместо мгновенного ContactStuck

NC провод при обрыве также выглядит как постоянный HIGH.

Поэтому текущая схема:

```text
HIGH при подъёме
-> FAULT_CONTACT_STUCK
-> полностью заморозить робот
```

не подходит.

Если нога поднялась:

```cpp
kContactReleaseCheckHeightMm = 10.0f;
```

или прошло, например:

```cpp
kContactReleaseTimeoutMs = 150;
```

но `released_event` так и не было:

```text
sensor health = SUSPECT_STUCK_HIGH
released_this_swing = false
```

Не воспринимать дальнейший HIGH как touchdown этого swing.

Для этого шага использовать номинальную open-loop swing trajectory до `expectedGroundZ`.

Не замораживать робот мгновенно.

После завершения шага запросить controlled stop.

Если это повторяется — отметить конкретный датчик `unhealthy`.

## 8. SENSOR_STUCK_LOW

Если:

```text
release был
DESCEND
GROUND_SEARCH
достигнут expectedGroundZ - 15 mm
contact так и не появился
```

это может быть либо настоящая яма, либо неисправность датчика.

Зафиксировать:

```text
NO_GROUND_OR_SENSOR_LOW
```

Не двигать ногу ниже.

Запросить controlled stop.

## 9. КРИТИЧЕСКИ: временно убрать contact из canStartSwing()

Сейчас `canStartSwing()` требует реальные HIGH от противоположного tripod и строит support polygon по instantaneous contact levels.

Для механических микриков это слишком жёстко и сейчас вероятно блокирует походку.

Добавить:

```cpp
enum class ContactMode {
    Disabled,
    TouchdownOnly,
    FullTerrain
};
```

Default сейчас:

```cpp
constexpr ContactMode kContactMode = ContactMode::TouchdownOnly;
```

В `TouchdownOnly`:

* tripod gait идёт по нормальной временной фазе;
* микрики НЕ разрешают и НЕ запрещают начало swing;
* support polygon НЕ блокирует gait;
* микрики используются только для:

  * release detection;
  * early touchdown;
  * normal touchdown;
  * ground search;
  * диагностики неисправного датчика.

`FullTerrain` оставить архитектурно на будущее.

## 10. Support polygon

Не удалять его код.

Но в `TouchdownOnly` не использовать instantaneous microswitch states в `canStartSwing()`.

В будущем `FullTerrain` должен строить support не непосредственно из GPIO, а из устойчивого состояния ноги:

```text
STANCE + confirmed touchdown
```

с отдельной временной hysteresis для потери support.

## 11. Controlled stop

Не переводить робот мгновенно в latched FAULT при проблеме одного контактного датчика.

Добавить:

```text
StopReason:
NONE
SENSOR_STUCK_HIGH
NO_GROUND
EARLY_COLLISION
SUPPORT_LOST
```

При recoverable contact problem:

```text
requested body velocity -> 0
не начинать новые swing
текущий безопасный swing закончить/вернуть
перейти в устойчивый IDLE
```

Только действительно критические ошибки IK/servo могут оставаться hard fault.

## 12. Удалить дублирование

Сейчас:

```cpp
applyTouchdownAdaptation()
```

из `contact_adaptation.cpp` нигде не используется.

Либо интегрировать его обязанности в новый `ContactManager`, либо удалить эту функцию.

Не оставлять две независимые contact architectures.

## 13. Diagnostics

Для каждой ноги нужно видеть:

```text
raw
stable
pressed_event
released_event
phase
released_this_swing
sensor_health
localGroundZ
```

Основной лог оставить компактным, например:

```text
contacts raw=111011 stable=111111
phase=S,S,L,S,S,L
event=--R---
health=OK,OK,OK,OK,OK,OK
```

Также:

```text
contact_mode=TOUCHDOWN_ONLY
stop_reason=NONE
```

## 14. Startup

При startup не считать текущий HIGH отдельным `pressed_event`.

Просто инициализировать stable level текущим физическим состоянием.

Первые события должны появиться только после реального изменения GPIO после startup.

## 15. Tests

Текущие идеальные contact tests недостаточны.

Добавить обязательно:

### Switch bounce

Последовательность вроде:

```text
LOW
HIGH 5ms
LOW 5ms
HIGH 5ms
LOW
```

не должна создать touchdown.

### Normal liftoff

```text
HIGH
начало LIFT
HIGH некоторое время
LOW stable 15 ms
```

должен появиться ровно один RELEASED.

### Normal touchdown

После release:

```text
LOW
DESCEND
HIGH stable 10 ms
```

ровно один PRESSED -> touchdown.

### HIGH в начале lift

HIGH сразу после начала swing не должен считаться touchdown или fault.

### Stuck HIGH

HIGH остаётся весь lift.

Ожидается:

```text
SENSOR_STUCK_HIGH
```

но не мгновенный global freeze.

### Stuck LOW / hole

release произошёл, но HIGH нет до конца ground search.

Ожидается controlled stop.

### Chatter during stance

Короткий LOW во время stance не должен остановить gait.

### Touchdown before DESCEND

PRESSED во время TRANSFER не должен превращаться в нормальный support touchdown.

## 16. Hardware test mode

Добавить:

```cpp
constexpr bool kContactDiagnosticMode = false;
```

При `true` сервы стоят в neutral, gait выключен, а USB показывает состояния шести датчиков.

Чтобы пользователь мог руками нажать каждый микрик и проверить:

```text
FL GP28
ML GP27
RL GP26
RR GP22
MR GP21
FR GP20
```

Для каждого должны правильно появляться:

```text
LOW -> RELEASED
HIGH -> PRESSED
```
